# 分层直连诊断

目标是找出失败层，不是不断换端口和协议。

| 层 | 检查 | 能说明什么 |
|---|---|---|
| 客户端 | 物理网卡公网 IPv6、默认路由、TUN/系统代理/环境代理 | 是否具备候选直连路径 |
| VPS | 真实地址/路由、服务监听、云防火墙、OS 防火墙 | 是否具备收包与回包条件 |
| TCP | 物理接口绑定的连接探测 | 是否到达 TCP 握手；不是 VPN 验收 |
| REALITY | 隔离客户端、匹配 UUID/SNI/公钥/short ID/flow/指纹 | 是否完成实际代理协议 |
| 出站 | 两个 IP 站点及实际连接链 | 是否保持固定出口且未套用其他代理 |
| 日常应用 | 激活的生产配置、TUN 的普通请求、手机实机 | 是否真正生效 |

`probe.py` 在 macOS 使用 IP_BOUND_IF/IPV6_BOUND_IF，在 Linux 使用 SO_BINDTODEVICE。若绑定失败，报告错误，不能静默退回不绑定测试。每个地址一次、超时 4 秒。不传接口时，结果明确标记可能经过 TUN。首次部署服务还未监听时不要把 TCP 443 拒绝/超时归因于网络封锁；先检查 SSH 端口和服务端状态。

## 绕开本机代理造成的假阳性

- curl 清除大小写 `http_proxy`、`https_proxy`、`all_proxy`、`no_proxy`；但这仍不能绕过 TUN。
- 物理直连验收：生成配置副本，给独立 Mihomo 设置 `interface-name` 为物理接口、`tun.enable=false`，删掉原 listeners，将 mixed-port 改为已确认空闲的 loopback 端口；控制 socket 和数据目录放入私有临时目录。
- 只保留被测节点，组改为仅含它的 select。启用前语法验证，启动后走该测试端口做 `verify.py`，记录入口家族和接口。完成后只结束自己的进程，删除临时含密钥配置。
- 再测生产配置 TUN；隔离测试通过不能替代日常验收。

## 失败后的决策

1. TCP 未建立时先查服务监听、防火墙、路由。必要且有管理员权限时，在本机物理接口和 VPS 同时抓取仅限目标地址/端口的短抓包，不采集整个 LAN。需要密码只能由用户输入安全的本机界面。
2. IPv4 不通而同一服务器 IPv6 可达：可用 IPv6 入口 + 原固定 IPv4 出口。Mac/手机分别检查 IPv6。`networksetup -getinfo` 可能信息滞后，应结合 `ifconfig` 和实际路由/连接。
3. 手机 5G 有 IPv6，不代表家庭 Wi-Fi 或热点也有；不要默认更改家庭路由器。路由器 RA/DHCPv6 往往影响全网，除非产品确有逐设备策略，否则不能声称只影响 Mac。
4. TCP 成功但 REALITY 失败时核对两端参数与客户端版本。X25519MLKEM768 等兼容字段按版本确认，不用关闭证书校验掩盖错误。
5. UDP 只有在用户希望尝试且存在可达证据时做一次有服务端对照的短测试；加密协议不能修复根本不可达的地址。无合法包到达不等于可精确定位某个防火墙设备。
6. 两种家族均不可达时，说明证据、限制和下一选项。用户要求不新增 VPS/不依赖机场时遵守约束；“代理通过”是另一条链路，不是原直连已经修复。

不把某个地区/某个地址的结果推广成所有 Vultr IP 均被封禁，也不保证另购 VPS 一定可达。
